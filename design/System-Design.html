The Signal System

A living design record. Updated whenever the system changes — see the Decision Log at the end.

Problem

Staying current on AI/ML means drowning in hundreds of clickbait articles a day, which produces FOMO and impostor anxiety and eats time that should go to building. Existing news apps make this worse — they are engineered to always surface something, which is the exact incentive that feeds the anxiety.

North Star

Kill FOMO, don't feed it. Success is the fewest items you'd regret missing — not the most items covered. The system is explicitly allowed to say "quiet day, go build." Two jobs: (a) be aware and understand why it matters (conversational currency), and (b) get hands-on and understand tradeoffs (weekly homework grounded in your repos).

High-level architecture

Five production agents on a pipeline, plus an eval/learning subsystem that measures the pipeline and adapts it to you over time.

Evals for the Framer — how the gate works

The harness answers one question: “did my last change break something that used to work?” It does that by holding the data still and re-running the current code against it.

  • The yardstick is frozen. data/evals/golden/2026-08-04/ is a copy of one past day — input, output and labels — that never changes. Today’s news flows through data/verified/ and data/briefs/ and never touches it.
  • What varies between runs is your system, not the data. Same seven items, same labels; only the prompt and code differ. So a red run can only have been caused by your edit — that attribution is the entire point.
  • It calls the real grader, not a copy: framer.check_faithfulness() is imported and invoked, so what you test is what runs. The stored verdicts in the frozen brief are historical and ignored.
  • It compares conclusions, not text. Labels match by pattern, so the grader may rephrase a claim freely; what must hold is the verdict.
  • Three checks: faithfulness (hard gate, ~$0.013) · structural assertions (hard gate, free — DO-THIS scope, example scope, sources, thread, counts recomputed with the Framer’s own functions) · usefulness rubric (soft, ~$0.006).
  • The output is an exit code. Non-zero blocks the change. A gate that cannot fail is not a gate — which is why the harness is itself tested by deliberately corrupting a copy and confirming it goes red.
  • Labels grow, never mutate. Every new bug becomes a permanent case; editing an old label to make a red test green deletes your own safety net.

Known gaps, all queued for Phase 6: the harness regrades the frozen brief, so a change to the Framer’s prompt is never exercised (needs a regenerate mode); flagged claims are surfaced but not regenerated (needs a bounded retry); and the free structural checks don’t run on live days (needs a daily smoke test). Also: every golden unit currently has expected_unsupported: [], so the missed-hallucination path is exercised only by manual negative tests, not automatically.

Agent · Scout DESIGNED

Discovers and ingests candidate items across the interest graph. In: config/scout-sources.md (Tier A–D seed list), config/profile.json. Process: fetch — likely via MCP servers for web/arXiv/GitHub — deduplicate, tag each item with its source and tier. Out: a raw candidate pool for the Gatekeeper. Graded on: recall — of what mattered, how much did it fetch. Its hard problem is that misses are invisible without an independent oracle.

Agent · Gatekeeper DESIGNED

Kills noise. In: Scout’s candidate pool. Process: provenance → corroboration (single-source rumour is held) → novelty dedup → reputation priors → materiality against the profile; everything killed is logged to the Suppressed drawer. Out: data/verified/gatekeeper_<date>.json — the contract the Framer consumes. Graded on: precision and recall, deliberately biased toward recall, because a false negative here is FOMO. Also owns the volume guard that protects the Framer’s single-call design.

Agent · Coach DESIGNED

Turns the week into practice. In: the week’s briefs + your GitHub repos. Process: pick one or two coherent concepts, design a 60-minute exercise (setup excluded), ground it in a real module or propose a new repo; runs Friday evening / Saturday morning so the expensive repo reasoning is batched. Out: backlog items in data/state/backlog.json. Graded on: code-grounding (assertion-checkable — does the module it names exist?) plus behavioural signals: completion rate, actual time, later reuse. Refactor due here: lift the faithfulness grader out of framer.py into a shared module rather than copying it.

Agent · Tuner DESIGNED

Learns your taste. In: signal/noise ratings, homework completions, and explicit “explore X” intent. Process: adjust source reputation and topic priors; assign credit backwards across a delayed pipeline; never act on n=1. Out: updated config/profile.json. Graded on: the slope of every other metric over weeks — it cannot be evaluated on a single run. Guardrails: a diversity floor against echo chambers, and no automated prompt edits — optimising to satisfy your own gate is how a system learns to write vaguer claims and pass.

Agent · Orchestrator DESIGNED

The front door, and the only agent wired to a live API. In: whatever you do in the UI — a dropped URL, a question, a rating, an intent. Process: classify intent and route (URL → Scout, question → chat over the brief, feedback → Tuner), collate responses, run checks. LLM-routed with deterministic fast-paths: explicit button actions dispatch directly; only ambiguous natural language needs the model. Out: answers to you, and labelled feedback into the eval dataset.

Extension points — adding the next agent

  • Code in agents/<name>.py; prompt and contract as prompts/<name>-prompt.md and -contract.md.
  • Write output to data/<stage>/<name>_<date>.json — named for the agent that produced it.
  • Reuse the shared plumbing: cost breaker + usage ledger, stop-reason guard, schema-enforced output, models pinned in top-of-file constants.
  • Add a golden case before the agent guards anything live; hard-gate the objective axis, keep the subjective axis reported until calibrated.

Evals — how we know it works

Every agent is measured, component-wise and end-to-end. The recurring split: objective checks (fixed gates, automatable) vs subjective checks (personal, learned targets).

AgentWhat we measureType
ScoutRecall — of what mattered, how much did it fetch? (invisible-miss problem → retrospective oracle)objective
GatekeeperPrecision & recall (classifier). Biased toward recall — false negatives = FOMOobjective
FramerFaithfulness (claim ledger → each claim carries a verbatim excerpt span; per-item vs own excerpt, thread vs the union; hard zero-hallucination gate) + Structural assertions (deterministic, no API) + Usefulness (rubric ratings, reported not gated until calibrated). The grader is itself under test against hand labels — see data/evals/obj + subj
CoachCode-grounding (assertions on your repo) + doability/skill (completion, actual time, reuse)obj + subj
TunerSlope of every other metric over time (meta-eval). Graded on trend, not levellongitudinal

Two grading modes: offline regression against a golden set of labeled past days (makes prompt iteration safe), and online production feedback (your ratings + a dashboard). The offline half is live as of Phase 3 — python data/evals/run_evals.py, exit code gates.

Who checks the checker. A grader is an agent too, and it fails the same ways. So it gets the same treatment: hand labels are the ground truth, the grader's verdicts are the prediction, and the harness reports its false positives and false negatives explicitly. Three habits fell out of finding two real false positives in our own graded output — make it show its work (enumerate every claim with a quoted span before judging), verify the evidence in code (a quoted span must literally appear in the excerpt), and give each unit only the ground truth it is entitled to (own excerpt for an item, the union for a thread that synthesizes across the day).

The eval / learning loop

Measurement and fixing are kept separate. The Evaluator is a read-only sensor; the Prescriber turns diagnoses into recommended actions; the Tuner is the actuator that recalibrates agents; the Control Room reports and asks you questions, whose answers become new gold labels.

Guardrail: anti-echo-chamber

The Tuner could raise your ratings by only feeding you what you already believe — a filter bubble that betrays the goal of balancing your thinking with new thinking. A standing diversity / exploration metric in the Control Room prevents this: a minimum share of items must sit outside your established priors.

Prescriber accountability

Every recommended action records a predicted impact with a confidence. After it ships, the Control Room shows predicted vs. actual — so the prescriptive layer earns trust instead of just asserting it, and every recalibration is regression-tested against the held-out set before shipping and is reversible.

System design & data

Data is separated from presentation. Agents write JSON to data/; the pages (Signal.html, Control-Hub.html) render it. Files: profile.json (the user profile), YYYY-MM-DD.json (immutable daily brief record + archive), backlog.json, metrics.json. Every record carries user_id.

Loop / token engineering: the daily path is cheap (small models for Scout/dedup, mid for Framer); the expensive repo-grounded synthesis (Coach) runs only Friday night / Saturday morning.

Tradeoffs (chosen deliberately)

  • Recall over precision at the Gatekeeper — better a little noise than a missed item (FOMO).
  • Depth over coverage in homework — one or two coherent exercises, the rest benched to the backlog.
  • Faithfulness is a hard gate; usefulness is a soft, learned target.
  • Build for one, don't hardcode one — profile object + user_id seam keep the multi-tenant path open at near-zero cost today.

Commercial path (documented, not built)

The brain transfers; the body doesn't. Agent logic is ~80% portable to a product; the local/single-user scaffolding is not. Key economics insight: most of the pipeline is shared — the news is the same for everyone, so run Scout → Gatekeeper once to produce a canonical verified pool, then apply a cheap per-user personalization layer (Framer framing + materiality + Coach) on top. What a product adds: auth + multi-tenant isolation, per-user LLM cost management, per-user cold-start onboarding, and cloud scheduling. Defensibility is the action loop (news → hands-on skill grounded in the user's code) and adaptive personalization — not the news itself.

Science methodology

Treat the system as an experiment: hypotheses (each agent's value), metrics (the evals above), controlled iteration (offline regression before shipping any prompt change), and honest reporting of predicted vs. actual. The append-only Decision Log below is the lab notebook.

2026-08-19

Root cause of the $965B false positive: grading scope, not carelessness. The grader was handed source_excerpt first and the framing second, and so enumerated the excerpt's claims and checked them against the excerpt — grading the ground truth against itself. It never read the framing, which is why a supported claim looked unsupported and, as a seeded fabrication test proved, why invented facts passed clean. Fixes: the writing under test comes first in the payload and is named writing_under_test; the excerpt is named ground_truth_excerpt; each claim must be phrased as the writing phrases it and carry a verbatim supporting span before any verdict; headlines are excluded (the Gatekeeper wrote them); and the day-level thread is graded against the union of every excerpt, never one item's. Flag lists are now derived in code from the claim ledger rather than taken as a second free-text field.

2026-08-19

Verify the verifier's evidence, in code. Every span the grader quotes is checked as a literal substring of the excerpt; a claim "supported" by a span that isn't there is downgraded to unsupported and recorded as a grader error, gated separately from false positives. A grader can invent a citation; a substring match cannot. Paired with temperature=0 on the grader — at default sampling it disagreed with itself on borderline sentences roughly one run in three, which would have failed builds at random (5/5 clean runs after; fabrication detection unaffected).

Three gaps found by walking the design, all deferred to Phase 6. (1) Flagged ≠ fixed — the Framer's faithfulness check surfaces unsupported claims but writes the brief anyway; the reflection loop is one turn, not a retry. (2) No daily check — run_evals.py only runs against frozen golden cases when something changes, so a contract violation on a live day goes unnoticed until the next prompt edit; the free structural checks should run daily as a smoke test. (3) The harness regression-tests the grader, not the writer — it regrades the frozen brief, so a change to the Framer's own prompt is never exercised. Closing that needs an opt-in "regenerate mode" that re-runs the Framer on the golden input before grading (costs one Opus call).

2026-08-19

Deterministic false-alarm signal added to the grader. When a claim is marked unsupported with no span, Python now scans the claim for numeric tokens (money, percentages, dates) and warns if they appear verbatim in the excerpt — the $965B case, catchable for free. It warns, never promotes: a number's presence says nothing about the claim built on it ("$122B" is in the excerpt; "SoftBank invested $122B" is still false). Proper nouns were dropped from the check — every claim names its own subject, so they fired on fabrications too. This is the only false-alarm signal code can produce: verifying evidence is present is mechanical; verifying it is absent is a semantic judgement Python cannot make.
