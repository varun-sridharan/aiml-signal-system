## How this file works

- **Rules, then runs, then debriefs.** A new run is a new `## Run N` section, added above
  "Debriefs" before the run starts, and it opens with its `/goal` start command.
- **A run writes only inside its own debrief markers**
  (`<!-- DEBRIEF:<date>:START -->` … `<!-- DEBRIEF:<date>:END -->`), which are added with an empty
  debrief when its run section is written. It never edits the rules, a run section, or another run's
  debrief. Its review step checks the diff of this file touches nothing outside its markers.
- **One run at a time.** Two runs writing this file at once would collide.
- **Debriefs are historical records.** They are kept exactly as their run wrote them; only their
  headings are shifted down three levels to nest here. Paths in them are the paths of the time:
  `AUTOPILOT.md` and `autopilot/runbooks/2026-10-17-m1-build.md` are now the standing rules plus Run 1
  below, `AUTOPILOT-2.md` and `autopilot/runbooks/2026-10-19-m1-closeout.md` are Run 2, and
  `DEBRIEF-2026-10-18.md` and `autopilot/debriefs/…` are the debriefs below. Evidence files stay in
  `autopilot/evidence/<date>/` and keep their paths.

## Standing rules

These rules were written for Run 1 on 2026-10-17 and apply to every M1 run.
Varun is away until morning. **Do not ask him anything.** Work through the steps below in order. Where
this file and `plan/plan.md` do not settle a question, take the most reversible option, record it under
"Decisions I made" in the debrief, and carry on.

The morning deliverable is the run's own debrief, inside its markers in this file: what was built, what is live, what
it cost, what was decided, and what is blocked. Keep it current **after every step**, not only at the end,
because the session may stop partway (see "If the session stops").

### What you may do without asking

- Write code, tests, schema and docs in this repo; commit as Varun; push to `main` with the push command
  below, and only after the full suite passes with `REQUIRE_DB=1`.
- Make paid API calls **only through `agents/llm.py`** (so every one is booked in the ledger), for: the
  Reader's web fetches, the eval gates, and one end-to-end weekly run.
- Open and close the Railway Postgres tunnel. Create tables through `agents/schema.sql`.
- Spawn subagents for review and QA.

**Design (added 2026-10-25).** Any new or changed page, template or component uses the brand kit in
`design/system/` (read its `readme.md` first; the project skill `.claude/skills/ai-ml-signal-design/`
says how). Colours, type and spacing come from its tokens, never hard-coded values.

### What you must never do

- Print, log or paste `DATABASE_URL`, any API key or any credential. Never commit `.env`. Run a secrets
  scan of the staged diff before every commit.
- Touch `data/evals/golden/`.
- Hand-edit the Claude Design snapshot pages (`application/*.html`, `design/*.html`). If a change makes
  one stale, list it in the debrief under "Stale artifacts".
- Force-push, rewrite history, or delete data outside a test's rolled-back transaction.
- Change Railway settings, the Claude Console, the claude.ai project memory, or the scheduled Weekly
  Digest. **The old digest keeps running in parallel; do not touch it.**
- Enable a recurring schedule for the new weekly run. Build the entrypoint and document how to schedule
  it; Varun switches it on.
- Send email or messages, or publish anywhere except this app's own pages.

### Setup (do first)

1. Keep the Mac awake for 12 hours: `caffeinate -ims -t 43200 &`
2. Open the tunnel:
   `(railway connect Postgres --tunnel-only --port 15432 >/dev/null 2>&1 &) ; for i in $(seq 1 15); do lsof -i :15432 >/dev/null && break; sleep 1; done`
   Before every test run, check `lsof -i :15432`; reopen it if it has dropped.
3. Record the starting point in the debrief: `git log --oneline -1`, the live `/health`, and the ledger's
   month-to-date spend (read it through `agents/budget.py`, and print the figure only).

**Tests:** `REQUIRE_DB=1 .venv/bin/python -m unittest discover -s tests -t .`

**Push command** (it never runs without the full suite passing):
`REQUIRE_DB=1 .venv/bin/python -m unittest discover -s tests -t . && git push`
Then poll `https://aiml-signal-system-production.up.railway.app/health` every 10 s, for up to 6 minutes,
until it shows the new sha. If it never does, open Railway's deploy logs through the CLI if you can (read
only), record the failure in the debrief, revert your last commit with a new commit, and push again.

### After every step

1. **Review.** Spawn a reviewer subagent with a fresh context. Give it the row, the diff and the test
   output, and ask it to be skeptical:
   - Does the work meet the row's Outcome?
   - Does every new test fail when the thing it checks is broken?
   - Are there secrets in the diff? Is there anything outside scope?

   Fix what it finds. Whatever you do not fix goes into the debrief under "Open review findings".
2. **Plan.** Update `plan/plan.md`:
   - set the row's status;
   - add a decision log entry for anything decided (newest first, at most five sentences);
   - update the Status paragraph;
   - run `python3 scripts/check_plan_format.py`.
3. **Commit and push.** Commit as Varun, with a message that names the row, then run the push command.
4. **Debrief.** Append the step's section to the debrief.

### Stop and skip rules

- **The same failure twice.** If two fix attempts fail, mark the step **Blocked** in the debrief, with
  the error and what you tried. Move on to the next step that does not depend on it. Steps 3 and 5 do not
  depend on step 2.
- **Spend.** If the ledger's month-to-date spend reaches **$35**, make no more paid calls. Finish the free
  work and record the spend.
- **Refused commands.** If a command needs approval that nobody is there to give, do not wait. Record the
  command and what it was for, and continue with something else.
- **Stopping for good.** Stop when nothing buildable is left. Go-live, the style row, the story video and
  turning off the old digest are Varun's steps, not this run's.

### If the session stops

On "continue", read the debrief's progress log and `git log`, re-run the setup (caffeinate and the tunnel),
and resume at the first step that is not complete. Never redo a step that is pushed and recorded.

---

### Debrief format

1. **The morning summary, in five lines.** What is live, what is not, what Varun must do first.
2. **Step table.** For each step: status (Done, Done pending review, Blocked, Not started), commit sha,
   and whether it is live.
3. **Live links** to check.
4. **Spend.** The ledger before and after, per step, and the cost estimate per weekly run.
5. **Decisions I made**, each with the reversible option taken and how to undo it.
6. **Blocked**, and what would unblock each.
7. **Open review findings.**
8. **QA verdicts** from step 7, unedited.
9. **Stale artifacts**: Design snapshot pages, README sections and roadmap entries that are now out of
   date.
10. **Questions for Varun.**
11. **Progress log.** One timestamped line per step.

### Lessons from run 1, now rules

1. **Never pipe the test run before `&&`.** `… | tail && git push` hides a failing exit code, and run 1
   pushed a red suite that way. Run the push command exactly as written, unpiped. If you want less
   output, write it to a file and read the file afterwards.
2. **Record evidence in files, not only in console output.** For every number the debrief claims
   (eval miss rates, mutation results, dry-run counts), save the raw output under `data/evals/runs/`
   or `autopilot/evidence/2026-10-20/`, and cite the path. The QA agent marked eight claims "Not verified"
   in run 1 for lack of exactly this.
3. **A gate is changed only with its own decision log entry**, saying what it accepted before and what
   it accepts now. No gate is loosened to get an edition published.
4. **Keep the step table current.** Run 1's table still said "Not started" for a step that had run.

### The work, in order

#### Step A · A failed week can be rerun (rows 8 and 11)

Today the run id is the week key, and a done stage is immutable, so a week whose gates fail can never
be reframed. Run 1 worked around this by publishing under an older key, `2026-W40`, which is why the
live edition is mislabelled.

- Let a week have numbered attempts: the run id becomes `2026-W43` for the first attempt and
  `2026-W43-r2`, `-r3` and so on for later ones. Widen the `runs.id` CHECK accordingly with an additive
  migration, and keep all the existing triggers. A new attempt starts at the Reader by default; add a
  `--reuse-reader <run-id>` option that starts from an earlier attempt's done Reader output, so a
  reframe does not re-fetch.
- At most one **published** edition per week. Publishing attempt 2 when attempt 1 already published is
  refused.
- **Label an edition by the window its Reader actually read**, stored in the Reader's output (for
  example "Oct 10 – Oct 18, 2026"), never by the run key. Fix how the live W40 edition displays: briefs
  are append-only, so derive the label from the stored Reader window or the publish date, and do not
  rewrite the brief.
- Mark superseded failed attempts in the status view. The W41 and W42 runs stay as they are; they are
  evidence.

#### Step B · The faithfulness gate catches the planted fabrication (row 10)

This is M1's exit criterion: "faithfulness and structural gates green on a golden week **including a
planted fabrication**". Today the grader misses the planted `$965B` in `negative-01` every time.

- Build `bk-retry` exactly as designed in `plan/roadmap.md`: **any lift on a unit retries that unit,
  once.** `lifted_claims()` already exists in `agents/framer.py`. Row 10's "port, do not extend" no
  longer applies: the port is done and verified, so a change now can be attributed.
- The design says it "ships with more negative cases, not before them". Add **at least three new
  planted-fabrication cases** (a changed number, a changed date, an invented attribution) under
  `data/evals/negative/`, as new files. **`data/evals/golden/` stays untouched.**
- **Measure it, five paid runs per case**, the same way the 2026-09-15 baseline did: the miss rate on
  each planted case, and the false positives on the clean golden day. Save the raw results to files.
  Done means every planted fabrication is caught in at least 4 of 5 runs with 0 false positives on the
  clean day. If it falls short, do not fit thresholds to pass: record the numbers, mark the step
  Blocked, and say what you would try next.
- Rerun the weekly gate tests. Paid-call spend for this step should stay under $3.

#### Step C · Sources from the old digest's catalogue (row 8)

`config/digest-sources.md` is the old digest's source catalogue, copied on 2026-10-19. It is the
"91-domain list".

- Seed `sources` from it, with tiers as labelled in the file, in addition to what is there now. Do not
  invent domains; a source the file names without a fetchable address is added as unaddressed.
- Add feeds or indexes for the labs and sources with none today, prioritising Anthropic's **two

  Where a site has no feed, use its index page through the web fetch path, with the dating rules in the
  file (some indexes show no dates; open the post to date it).
- Turn the file's "fetch and dating rules" into code where they are mechanical: the known-blocked
  domains, never guessing slugs, the primary source's date over coverage dates.
- Keep the per-run fetch cap and the $3 per-run ceiling. Record the new candidate counts from a free
  dry run, saved to a file.
